Project purpose

Add exaggeration to existing animations

We built the plug-in for small teams working with existing animation assets. Users select Regions and Chains and configure Response Rules; motion analysis or gameplay requests then trigger GPU mesh deformation. Effects can be reused without changing the source animation.

04Deform

Execute ordered RDG passes and output the deformed mesh.

Design target

Control deformation by Region and camera direction

Regions and Chains limit the deformation area. Optional camera-aware guards keep the action direction visible, and rules select each Module and its strength while preserving the source animation.

Program architecture

From final-pose snapshot to vertex output

The Game Thread stores the final pose in a Snapshot and calculates normalized motion signals. Authored Phase Curves and Markers take priority over automatic analysis. Slot arbitration resolves explicit Effect Requests alongside pose-driven responses, then value-copied Work Items pass to ordered RDG passes on the Render Thread.

01, Runtime

Analysis and response

After animation evaluation, stores the required control-point component-space pose, component transform, sample time, serial, and continuity. It derives Region, tip, angular, and chain features, normalizes linear thresholds by Region scale, then resolves phase timing before Response Rules and Module weights.

02, Render / GPU

Ordered deformation

Resolved work moves to the Render Thread and is filtered by Scene and Execution Group. Compute passes execute in order at the MeshDeformer stage.

03, Editor

Per-Asset effect settings

One Asset Editor provides Bone Group, Module Stack, and Response Rule settings alongside Preview Mode and diagnostics.

04

Core system, Motion timing

Convert final-pose motion into six-stage timing signals

The Motion Phase Analyzer samples the final evaluated pose by Region and derives linear, tip, angular, acceleration, and Chain-extension signals. Temporal confirmation, cycle history, and Region ownership turn those signals into Phase, strength, direction, and cycle data for Response Rules.

01Starting Pose

Quiet pose or return point that arms the next cycle.

02Anticipation

Preparation confirmed by acceleration, Chain contraction, or counter-motion.

03Action

The stroke along the predicted motion axis reaches the action threshold.

04Overshoot

Energy falls after the peak while the action direction is retained.

05Recoil

Recovery motion reverses against the action axis.

06Settle Pose

Low energy and pose return close the cycle.

01, Motion input

Measure articulation without Actor travel

The default Skeleton-root-relative mode removes Actor movement and extracted root motion while preserving shoulder, limb, and spine articulation. Full Final Pose mode remains available when whole-body travel should drive the cycle.

02, Temporal stability

Treat threshold crossings as candidates

Adaptive Trend Smoothing filters the signal. Confirmation windows, minimum Stage duration, and Cycle history then check the transition so a single noisy frame does not trigger peak deformation.

03, Analysis output

Keep detection separate from presentation

Response Rules map Phase, strength, direction, Region, and Cycle ID from the Analyzer to the ordered Module Stack. Effects can be adjusted without changing phase detection.

Editor controls

Start from a preset, then tune the asset

Conservative, Balanced, and Sensitive presets set the Entry, Preparation, Action, and Settle thresholds together. Editing a threshold classifies the setting as Custom, and every change is committed to the active Deformer Asset.

Conservative
Requires a stronger sustained signal before opening an automatic cycle.
Balanced
Default settings for typical character attacks and actions.
Sensitive
Detects smaller or slower motion with lower thresholds.
Custom
Preserves manually tuned thresholds in the asset.

Motion Phase troubleshooting, One-frame spike

Require temporal confirmation before Action

Problem
High energy in the first frame could trigger Action and peak deformation before the preparation motion.
Cause
The threshold check did not distinguish a single spike from motion continuing into the next sample.
Change
Changed the transition to start with zero-strength Anticipation on the first sample and enter Action only if the next sample confirms continued motion.
Result
With fixed test inputs, the 16ms sample remains in Anticipation and the 32ms sample enters Action.

05

Core logic and troubleshooting

Problems solved during development

I fixed errors involving frame delays, Region selection, and Render Thread timing while processing animation signals. The cases below describe their causes, the changes, and the results.

Case 01, Pose timeline

Recover from hitches without replaying stale poses

Problem
After a frame hitch, fixed-step catch-up could replay old component-space poses as current motion.
Cause
The accumulator was bounded, but stale samples still needed to be rejected by comparing pose timestamps with consumption time.
Change
Capped accumulated time and substeps, then reset stale, discontinuous, or teleported pose sources before rebuilding the sampling timeline.
Result
Signal processing resumes from the current pose. Pose Gap and Hitch Recovery regression tests cover recovery after the interruption.
OverAnimSimulationTypes.hPose lifetime guard
const double SampleAgeSeconds =
    ConsumerTimeSeconds - SampleTimeSeconds;
const double MaximumAgeSeconds =
    static_cast<double>(
        GetSanitizedMaxAccumulatedTime());

return SampleAgeSeconds >
    MaximumAgeSeconds + UE_DOUBLE_SMALL_NUMBER;

Case 02, Region selection

Stop repeated Region owner switching

Problem
Regions with similar scores could exchange ownership on adjacent frames.
Cause
Selecting only the current maximum provided no hysteresis.
Change
Kept the active Region unless a challenger exceeded both the relative and absolute switching margin; the following phase signal then confirms the candidate.
Result
Small score changes preserve the active owner while decisive counter-motion can still take priority.
OverAnimMotionPhaseAnalyzer.cppRegion switching guard
constexpr float ChallengerRelativeAdvantage = 0.15f;
constexpr float ChallengerAbsoluteAdvantage = 0.02f;
const float RequiredChallengerScore = ActiveScore +
    FMath::Max(
        ActiveScore * ChallengerRelativeAdvantage,
        ChallengerAbsoluteAdvantage);

if (!bCounterMotionPriority &&
    BestScore < RequiredChallengerScore)
{
    BestCandidateIndex = ActiveCandidateIndex;
}

Case 03, Async teardown

Cancel queued GPU work when its component is destroyed

Problem
A component could be removed while its deformer work item was still waiting in the Render Thread queue.
Cause
The shared queue had no component-specific cancellation path, so stale work could survive teardown and skip the source-skinning fallback.
Change
Enqueued the component ID to the Render Thread, removed every matching work item there, and executed each fallback delegate.
Result
Pending deformation work is removed after component teardown; a Cancellation regression test verifies fallback execution.
OverAnimDeformerTaskWorker.cppQueued-work cancellation
for (int32 Index = WorkItems.Num() - 1; Index >= 0; --Index)
{
    if (WorkItems[Index].ComponentId != ComponentId)
    {
        continue;
    }

    FOverAnimDeformerWorkItem CancelledWork =
        MoveTemp(WorkItems[Index]);
    WorkItems.RemoveAtSwap(Index);
    CancelledWork.FallbackDelegate.ExecuteIfBound();
}

Case 04, Socket attachment

Keep visual attachments on deformed endpoints

Problem
A socket-attached visual still followed the undeformed skeleton while Squash & Stretch moved the visible endpoint.
Cause
GPU vertex deformation does not modify the source socket transform.
Change
Exported a visual-only component-space offset, converted it to world space, subtracted the previously applied offset, and skipped physics-driven targets.
Result
Registered visuals follow the deformed endpoint without accumulating a per-frame location error.
OverAnimComponent.cppAttachment offset update
FVisualAttachmentState& State =
    VisualAttachmentStates.FindOrAdd(Entry.Key);
const FVector BaseLocation =
    Component->GetComponentLocation() -
    State.AppliedOffsetWS;

if (!NewOffsetWS.Equals(
        State.AppliedOffsetWS,
        UE_KINDA_SMALL_NUMBER))
{
    Component->SetWorldLocation(
        BaseLocation + NewOffsetWS,
        false, nullptr,
        ETeleportType::TeleportPhysics);
}

State.AppliedOffsetWS = NewOffsetWS;

Case 05, Response arbitration

Resolve competing effects in the same Slot

Problem
Motion, impact, and gameplay rules could target the same response slot during one frame, making update order decide the visible deformation.
Cause
Applying each request immediately gave no frame-wide view of conflicts.
Change
Collected requests first, grouped them by slot, then selected by priority and resolved magnitude before executing the Module Stack.
Result
Each Slot receives one Request selected by the arbitration rules, while effects in separate Slots can still be combined.
OverAnimEffectRequestTypes.cppPer-slot arbitration
FOverAnimEffectRequest& ExistingRequest =
    OutResolvedRequests[*ExistingIndex];
const bool bHasHigherPriority =
    Request.Priority > ExistingRequest.Priority;
const bool bHasSamePriority =
    Request.Priority == ExistingRequest.Priority;
const bool bHasStrongerMagnitude =
    Request.ResolvedMagnitude >
    ExistingRequest.ResolvedMagnitude;

if (bHasHigherPriority ||
    (bHasSamePriority && bHasStrongerMagnitude))
{
    ExistingRequest = Request;
}

Case 06, Collision signals

Collapse repeated contact callbacks into one impact response

Problem
One physical contact could produce several hit callbacks and stack the same deformation pulse.
Cause
The Physics Event Stream could report several Contacts for the same Gameplay Impact.
Change
Used a bounded Impact History to compare source component, signal route, bone, contact position, and time. A materially stronger follow-up hit bypasses duplicate suppression.
Result
Repeated callbacks no longer stack the same deformation; stronger follow-up impacts still reach the response system.
OverAnimComponent.cppImpact deduplication
const bool bSameSource =
    Entry.SourceComponent.Get() == SourceComponent;
const bool bSameRoute =
    Entry.SignalName == SignalName &&
    Entry.BoneName == HitResult.BoneName;
const bool bNearbyContact = FVector::DistSquared(
    Entry.ContactPointWS,
    HitResult.ImpactPoint) <= MergeDistanceSquared;

if (bSameSource && bSameRoute && bNearbyContact &&
    Magnitude < Entry.Magnitude * BypassRatio)
{
    return true;
}

Case 07, Global shader compile

Restore the missing platform root for the Region Blend shader

Problem
The Region Blend global compute shader failed to compile under DX12 / SM6.
Cause
The shader source began with parameter declarations without importing Unreal's platform root definitions.
Change
Added the engine Platform include at the shader entry file, leaving the existing FRegionBlendCS registration and RDG dispatch path intact.
Result
FRegionBlendCS compiles under DX12 / SM6 and continues through the existing RDG dispatch path.
